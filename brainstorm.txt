==========================================================================
PART 1. THE THREE TESTS
==========================================================================

"Efficient, easy, reliable" only helps if we can measure it. So:

EFFICIENT means
  - Tokens spent by Tuloy in a day. Today: 350 per ping, 3 to 4 pings a day,
    plus any you send by hand to refresh the number.
  - Programs Tuloy starts in an hour. Every ping or check starts the claude
    program. Fewer is better.
  - How often Tuloy wakes up when nothing can happen.

EASY means
  - Clicks to do the common thing (see usage, ping now, fix a problem).
  - A newcomer can do it without being told. Test: hand it to someone who
    has never seen it and watch, saying nothing.
  - No word they have to look up.

RELIABLE means
  - Every situation has an automatic test that fails if we break it.
  - When Tuloy doesn't know something, it says so. It never shows a guess
    as a fact.
  - A Claude Code update can't silently break it.

HOW WE DECIDE A ROUTE IS BEST
  For every plan below:
    1. List the real options, not just the first idea.
    2. Name what we don't know.
    3. Find the cheapest experiment that settles it, and run that first.
    4. Pick a number that says whether it worked.
    5. Write "done when" before starting.
  If an experiment disagrees with the plan, the plan changes, not the
  experiment.

FROM CLAUDE CODE'S DOCUMENTATION (looked up for this plan)

     model. If /usage reports that, it cost no tokens. Not yet seen for
     real.

     limited. When that fails, it shows the last numbers this Mac loaded in
     the past 60 minutes, with a "Showing last-known usage" note.

     in the docs says the desktop app runs it.

  l. Sign-in is interactive: it may ask you to press a key to copy a link,
     or to paste a code. It keeps the login in the macOS Keychain. That
     makes "sign in without Terminal" [34] risky.

PART 3. FIVE EXPERIMENTS BEFORE ANY CODE
==========================================================================

Each takes minutes and can change a plan. You run them in Terminal (your
Terminal is signed in; my session isn't, and I shouldn't spend your tokens
finding out).

E1. DOES /usage COST NOTHING?                            decides [1] [83]

    cd ~/.tuloy
    time claude -p "/usage" --output-format json

    Look for:
      - "result": does it contain your percentages and reset times?
      - "usage" / "total_cost_usd": are the token counts zero?
      - "local_command": is it there? (means no model was asked)
      - "num_turns": 0 or 1?
      - how long it took
    Then compare its number with Claude's own usage page. Same?

    Run it again as:
      claude -p "/usage" --output-format stream-json --verbose
    and look for a line with "rate_limit_event". If /usage produces one,
    Tuloy can read it with the code it already has and never has to read
    human text. That would be the best possible outcome.

    Outcomes:
      A  zero tokens, numbers present     -> build [1] on it
      B  numbers present, costs tokens    -> no better than a ping; go to
                                             the fallback in [1]
      C  doesn't work this way            -> fallback in [1]

E2. IS THE ROUNDING 5, 10 OR 20 MINUTES?                 decides [5]

    Next time no window is open and you'd start one anyway, choose Ping Now
    at a minute ending in 5 to 9 (say 2:17). Note the reset Tuloy reports.
      reset 7:10  -> 10-minute marks  (expected)
      reset 7:15  -> 5-minute marks
      reset 7:00  -> 20-minute marks or the hour after all
    One ping, 350 tokens, one answer.

E3. DO HOOKS RUN IN THE DESKTOP APP?                     decides [1] [8]

    Add this to ~/.claude/settings.json by hand (I can give the exact text
    when we get there):
      a "Stop" hook whose command is:  touch ~/.tuloy/activity
    Send one message in the desktop app's Code tab, then:
      ls -l ~/.tuloy/activity
    If the file's time is "just now", Claude Code can tell Tuloy the moment
    you use it. Try the same from Terminal, and from a normal chat (which I
    expect will NOT do it).

E4. DOES A POPOVER BEHAVE?                               decides [62]

    A one-hour throwaway build in demo mode that swaps the menu for a
    panel. Three questions only:
      1. Can the panel close itself when you click "Open Tuloy"?
      2. Do the Tuloy windows still open from it?
      3. Does it resize cleanly when a problem line appears?
    Thrown away afterwards whatever the answers.

E5. CAN TULOY RUN THE SIGN-IN ITSELF?    (optional)      decides [34]

    Only if we still want [34] after [33] is in. Run the sign-in with no
    terminal attached and see whether it opens the browser and finishes, or
    stalls waiting for a key press.

[145] TEST THE BRAIN, NOT JUST THE PARTS                         STAGE 1
--------------------------------------------------------------------------
WHY
  The schedule, the decision and the readers each have tests. What Tuloy
  does with a ping's result (save it, retry, rest, plan the next one, notify)
  has none. That is exactly the part every other item here changes.

TODAY
  All of it lives in AppModel, wired straight to the real clock, the real
  claude program, real saved settings and real notifications. A test can't
  get in between.

OPTIONS
  a. Test through the screen (click buttons, read text). Slow and brittle.
  b. Leave it and test by hand. That's how the 8 pointless retries shipped.
  c. Give the brain four sockets it plugs into, and plug in pretend ones
     for tests.

RECOMMENDED: c
  The four sockets:
    Clock      "what time is it?"        real: the Mac    test: we set it
    Claude     "ping" and "check"        real: claude     test: scripted
    Storage    "save" and "load"         real: prefs      test: in memory
    Notices    "notify"                  real: macOS      test: a list
  Move the ping-handling out of AppModel into a small piece with no screen
  code (call it the Engine). AppModel keeps the settings and feeds the
  screens.

STEPS
  1. Write the scenarios below as plain sentences first. Agree them.
  2. Add the four sockets with the real ones plugged in. Behaviour must not
     change; all 97 current tests still pass.
  3. Move ping handling into the Engine. Still no behaviour change.
  4. Write one test per scenario using the pretend sockets.
  5. Only then start on [14].

  Scenarios to cover (each becomes a test):
     1. Scheduled ping works: window saved, next ping planned, history +1.
     2. Ping works but reports no window: an estimate is saved, marked so.
     3. Ping at the window limit: counted as delivered, 100%.
     4. Week used up: rest until reset, no more pings, one history line.
     5. Offline at ping time: no attempt; goes out when back online.
     6. Ping fails, will fix itself: retries at 1, 2, 5, 15, 30 minutes.
     7. Ping fails, needs you: ONE attempt, then silence          [14]
     8. You sign in: one ping, within a minute                    [14]
     9. Mac asleep at ping time, wakes 2 hours late: pings.
    10. Wakes 6 hours late: skips, plans tomorrow.
    11. A window is already open at ping time: waits, pings when it ends.
    12. Keep going: pings at each reset until the stop time.
    13. Ping Now while a scheduled ping is waiting: counts for both.
    14. Pause, then resume: nothing sent late.
    15. Schedule changed mid-day: plans again, hold cleared.
    16. Lean ping fails "unknown option": plain used, and remembered [15]
    17. Claude Code version changed, then failure: the message says so [26]

CHECK IT'S THE BEST ROUTE
  - Replay 5 October. Feed the Engine exactly what happened: signed out at
    4:42 PM, keep going on. Today's code must reproduce the 8 automatic
    tries (that proves the test sees what really happened). After [14] it
    must show 1.
  - Count: every "if" in the ping handling is reached by some test.
  - The whole suite still runs in a couple of seconds.

DONE WHEN
  17 scenario tests pass with the real behaviour unchanged, and a mistake
  deliberately put into the retry rule makes a test fail.

[14] STOP RETRYING WHEN ONLY YOU CAN FIX IT                      STAGE 1
--------------------------------------------------------------------------
WHY
  Signed out, not installed, wrong account: no retry can succeed. On your
  first day Tuloy tried 8 more times anyway. Each try starts the claude
  program three times.

TODAY
  Every failure, whatever the cause, retries after 1, 2, 5, 15, then 30
  minutes for as long as a ping is wanted.

OPTIONS
  a. Fewer retries for everything. Hurts the cases where retrying works.
  b. Sort failures into "fixes itself" and "needs you". Retry the first,
     wait for the second.
  c. Never ping unless the sign-in check says ready. Sounds neat, but that
     check has been wrong before (it said ready while a ping failed).

RECOMMENDED: b, with the check as the "you've fixed it" signal

  What happened                Retry by itself?        Try again when
  -------------------------    --------------------    ----------------------
  Claude Code not found        no                      the check finds it
  Signed out                   no                      the check says signed in
  API key, not your plan       no                      the check says plan
  Signed in, ping refused      once, at the next       a ping works
                               scheduled time
  Claude Code too old          no                      its version changes
  Offline                      waits for the network   it comes back
  Took too long                yes: 1, 2, 5, 15, 30    -
  Anything else                yes, 5 tries, then      -
                               once an hour
  Week used up                 no                      the week resets

  While waiting on you, Tuloy runs the FREE sign-in check (no message
  sent): every 5 minutes for the first hour, then every 30. Also at once
  when you open a Tuloy window, when the sign-in script finishes [33], and
  when the Mac wakes. Ping Now always works, whatever the state.

STEPS
  1. Give each failure a retry rule (the table), in one place.
  2. Add a "waiting on you" state that the decision respects.
  3. Add the gentle repeated check while in that state.
  4. When the check passes: clear the state, ping once if one is wanted.
  5. Home and the menu say "Waiting for you to sign in", not "retrying".

CHECK IT'S THE BEST ROUTE
  - Scenario tests 7 and 8 from [145].
  - The 5 October replay: 8 automatic tries become 1.
  - Count programs started in the first hour of waiting on you: today 18
    (6 tries, 3 programs each); target 12 or fewer, all of them the free
    check, and none that send a message.
  - Check option c is really worse: write the test "check says ready, ping
    refused" and confirm b still reports it and c would hide it.

DONE WHEN
  Signed out for a whole day costs one failed ping and one notification,
  and signing in is followed by a working ping within a minute.

NEEDS  [145]

[26] SAY WHEN CLAUDE CODE UPDATED                                STAGE 1
--------------------------------------------------------------------------
WHY
  Claude Code updates itself. Its docs already warn of a coming change that
  would stop pings using your login. When that day comes, "sign in" would
  be the wrong advice, and you'd have no way to know.

RECOMMENDED

  ping fails and the version is different from the last good one, add one
  line to the problem:
    "This started after Claude Code updated from 2.1.288 to 2.2.0."

  1. Version comes free with each ping; save the last good one.
  2. On failure, ask Claude Code its version (instant, free) and compare.
  3. Add the line to the menu, Home, and the notification.
  4. Put the version in "Copy details for support" later.

CHECK IT'S THE BEST ROUTE
  - Scenario 17.
  - It must never claim an update caused a failure when the version is the
    same. Test that too.

DONE WHEN
  The first failure after an update names both versions.

==========================================================================
PART 7. WHAT COULD GO WRONG
==========================================================================

  /usage turns out to cost tokens, or isn't readable.
      Then [1] becomes the fallback, [83] is weaker, and [74] isn't
      possible. E1 tells us in five minutes.

  Claude Code changes /usage's wording.
      The reader gives up cleanly, Home says usage can't be read, pings
      carry on as today. Never a wrong number.

  The usage service gets tired of being asked.
      Tuloy backs off to 15 minutes when Claude Code reports "last-known
      usage", and never asks more than every 3 minutes.

  Hooks don't run in the desktop app after all.
      The timer still covers it, just less promptly. E3 tells us.

  The popover can't close itself cleanly.
      Build the menu bar item by hand (option b). About a day more.

  More moving parts means more to break.
      That's what stage 1 is for. Nothing from stage 2 on is started until
      the brain has tests.

  We build too much at once.
      One stage at a time, each followed by a day of real use.
